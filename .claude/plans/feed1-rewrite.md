# Plan: Rewrite FMcord as "feed1" — TypeScript, clean architecture, same core behavior

## Context

FMcord is a ~17,300-line Last.fm Discord bot on EOL discord.js v12 / Sequelize v5, with 95 command files that are largely copy-pasted variants of each other (`fm.js`/`f.js` are byte-identical 53KB files; crown logic is duplicated across 6+ files). It is buggy for structural reasons: no locking on crown read-modify-write, numeric counts stored as strings (NaN comparisons), a job queue that deletes items before processing them, and hardcoded IDs everywhere. The owner (Matt) wants a clean rewrite named **feed1** keeping core functionality: now-playing/profile, tops/who-knows/charts, the full crowns system, and RYM link commands. Fresh DB (data migration later). Deploy target: Oracle Cloud Always Free ARM VM via GitHub Actions. Prefix commands stay (`&`, config-driven); no slash commands.

## Investigation findings

Five parallel deep-reads of the old codebase produced these load-bearing facts:

### Core infrastructure (bot.js, events, utils)
- Routing: global config prefix, `message.author.bot` guard, command matched by **filename** in a Collection — no alias mechanism; every alias is a duplicated file (`src/events/message.js:2-9`, `bot.js:291-298`).
- No cooldowns exist anywhere active; `src/classes/Command.js` is dead aspirational code never imported by commands.
- Disable system: `disables` table (`guildID`, `channelID`, `cmdName`, `guildDisabled`), checked in `message.js:10-26`; DMs bypass checks. The **writer commands are retired** (`src/retired commands/disable.js`/`enable.js`, gated on MANAGE_GUILD) — the table is frozen at runtime.
- Error reporting: `console.error` and `process.stderr.write` are monkey-patched to post to a hardcoded error channel `1350524158915776604` (`bot.js:42-67, 425-450`); status channel `1350523912085311560`; global uncaughtException/unhandledRejection handlers; custom reconnect loop + 30s heartbeat (`bot.js:103-160`).
- User mapping: `users.discordUserID → lastFMUsername` via `Fetchuser` class; unregistered → falsy, commands reply `client.snippets.noLogin`. Mention convention: `args[0] ? message.mentions.users.first() : message.author` (fragile: non-mention arg → undefined).
- Startup quirks to drop: Glitch keep-alive express server (`bot.js:233-242`), commented-out DBL, raw-SQL `times` table rebuild on every boot (`bot.js:329-351`) which **fights the only migration** (migration casts `ms` to INTEGER, boot recreates as TEXT), fake-message queue kickoff impersonating the owner (`bot.js:177-231`), owner `eval` command (RCE surface).
- Backups: 12-hourly copy of the SQLite file + users CSV, keep 20, report to Discord channel (`backup_db.js`).

### fm / profile commands
- `fm.js` and `f.js` are byte-identical except the help block; `ft.js` and `src/f BACKUP.js` are older copies. One implementation, alias table.
- `&fm` output: embed with author = Discord name/avatar linking to Last.fm profile, color = member's role color, title = bold track name, description = artist as Google-RYM-search hyperlink + album as hyperlink or literal `[no album]`, thumbnail = `track.image[2]`, footer `scrobbles → all: N | artist: N | album: N` (segments dropped when 0) plus `album ranks → w: #N | m: #N | y: #N | o: #N` lines (`src/commands/fm.js:30-38, 138-151, 213-399`).
- Two-phase render: posts "loading your data..." embed with spinner gif, then edits in place. Footer icon = one of three gifs encoding album-crown state (default `GBuQOhn`, you-own `bCeKwDd`, other-owns `Qgo8myA`) (`fm.js:37-44, 81-88`).
- `*` in names is replaced with the literal string `&ast` everywhere to defeat markdown italics.
- **`&fm` is not read-only**: every invocation runs a full guild-wide crown recomputation for both album and artist (one API call per registered member) and can emit crownWon/crownTaken DMs (`fm.js:689-1177`).
- Not-playing fallback: last scrobbled track with footer `cannot fetch currently playing track.\nthis is the last track scrobbled.`; final fallback plain text `an error occurred. Last.fm may be experiencing issues at the moment.`
- `&login <lastfm> | <rym>`: validates via `user.getInfo` only (no auth), rejects if already registered; `&logout` deletes row; `&mylogin`, `&lfm [@user]`, `&plays`/`&p` (plain-text reply), `&list <artists|songs> <period> <N>` (embed, numbered list).
- No reactions on fm posts (ReactionInterface imported but unused there).

### Tops / who-knows / charts
- Chart family: `w/m/3m/6m/y/o` are 5-line wrappers over `chartUtils.generateChart(period)`; weekly = 5x6 grid, rest 5x10; 100px tiles from `getTopAlbums` `image[3]`, fallback `images/no_album.png`; text overlay with color coding (green `!! NEW !!`, yellow/magenta crowned `♛`, cyan stats), stats footer (scrobbles, per-day avg, coverage %, new count, crown count); progress reactions 1️⃣2️⃣3️⃣❗ (`src/utils/chartUtils.js:31-313, 462-540`). `chart.js`/`nt.js` are legacy/no-titles variants with own canvas code.
- Every chart run calls `processQueues` — enqueues the user's top albums/artists (up to 5 pages × 250) into `albumqueues`/`artistqueues` for later crown recompute, snapshotting the **entire guild member list as delimited strings** per row (`chartUtils.js:315-454`).
- Who-knows: `wk.js` (artist) / `a.js` (album, missing help block) — fetch all guild members, one **sequential** Last.fm getInfo per registered member, sort desc (ties alphabetical), top-10 embed `N. name → **plays** scrobbles (pct%)` with totals footer and pagination; then crown create/update/transfer logic inline (`wk.js:142-539`).
- "My #N ranked" family: 12 near-identical files (`aw/am/a3m/a6m/ay/ao` albums, `ar*` artists) varying only by period + random ceiling. Known bugs: `a6m.js:50` passes `3month` (should be 6), `ao.js:7`/`aro.js:7` pass an **undeclared period** (undefined → Last.fm defaults to overall, accidentally correct).
- Crown-list/leaderboard: `c.js`/`ac.js` (per-user crowns, paginated, sort flags; performs turl-shortening **writes during read**), `cb.js`/`acb.js` (guild leaderboards with fragile `userID + '#@^!&*' + username` string keys); `act.js`/`actt.js` are duplicates of `ac.js`.

### Crowns
- `crowns` unique on (guildID, artistName); `acrowns` unique on (guildID, artistName, albumName). **All counts stored as STRING** → parseInt/NaN comparison bugs (e.g. `wk.js:343` takeover condition misfires on stale/empty values).
- Three racing write paths (live who-knows, `&fm` opportunistic, background queue) with findOne → seconds of API calls → update, no transaction/lock; last-writer-wins regressions.
- Queue engine `queueProcessor.js`: infinite loop, `findAll()[0]`, **destroy row then process** (crash = silently lost item), retry ×3 with backoff only on Last.fm codes 8/29/16, 10s between items, 5min idle poll; errors to hardcoded channel. Both processors are **auto-started at boot** via fake message objects impersonating the owner (`bot.js:168-231`); the `--r` owner gate (`artq.js:338-343`) additionally allows manual starts, so a second invocation spawns a **duplicate worker** — nothing enforces singleton processing.
- Crown creation rules diverge by kind: artist crowns are created **with no minimum plays** (`wk.js:265-271`); album crowns require `plays > 0` (`a.js:290`).
- Chart queue paging: capped at 5 pages of 250, except guilds `447838857606463489` and `671074176622264320` get `Infinity` (`chartUtils.js:333`) — the latter is Matt's own server, so unlimited depth there is intentional owner behavior.
- Takeover rules: new crown created for top listener (artist path has **no minimum plays**; album path requires >0); owner-left → unconditional reassign; owner-present → transfer when challenger strictly exceeds, with a re-verify loop (up to 10 API re-queries) that lets the incumbent keep on tie. `a.js:365` runs the second branch even after the first reassigns (not `else if`) — divergence from `wk.js:343`.
- Notifications: opt-in tables `notifs` (loss) / `wnotifs` (win), toggled by `&notifyloss`(+ duplicate `&notify`)/`&notifywin`; events DM prev/new owner only when opted in and both registered; **album-vs-artist wording decided by whether an album API call throws** (`crownWon.js:17-39`).
- Telemetry: `times` rows (ms per scan) + `totalsAndAvgs` rolling averages feed ETA displays in `artq`/`albq`; audit rows in `artistrecords`/`albumrecords`.

### DB / RYM
- Live tables: users, crowns, acrowns, artists, albums (URL caches), notifs, wnotifs, artistqueues, albumqueues, times, totalsAndAvgs, artistrecords, albumrecords, disables (read-only).
- Vestigial (drop): `ryms` table (never written; RYM identity lives on `users.RYMUsername`), `guesses`, extensionless `src/models/TotalsAndAvgs` file, `users.RYMmaxplus` column.
- RYM feature = pure URL building off `users` columns (`RYMUsername`, `RYMPerpage`, `RYMmax`, `Wishmax`, `Tagmax`, `Tag`, `Chart`): setup commands `login/rpp/max/wmax/tset/tmax/chset/ch`; link commands `rym/rstat(s)/rcomp/rr/ry/rg/rart/rw/wg/rn`; randomizers `rand/wrand/trand/srand` (embeds + reaction paging). Mostly plain-text `` `<user>'s` <thing>: <url> `` replies. `sc.js` has hardcoded per-guild username lists — drop.

## Approach

Clean-room TypeScript rewrite in this repo on branch `matt/feed1-rewrite`, new code under `src/` after moving the old tree to `legacy/` (kept for reference during the rewrite, deleted before merge... no — kept in git history only; the working tree gets fully replaced). Old behavior is the spec; the findings above enumerate exactly what to preserve verbatim (output formats, gifs, `&ast` escaping, fallback strings) versus what to deliberately fix (types, races, queue loss, duplicate files).

The architectural core that kills the bug classes:

1. **One command registry with aliases and generated period variants** — `fm`+`f` is one definition; the 12 "my #N ranked" files become one definition × config table; chart periods likewise. ~95 files → ~25 definitions.
2. **One crown service** as the *only* write path to crowns tables, with a per-`(guildID, artistName[, albumName])` in-process mutex (single bot instance, so in-process serialization is sufficient — better-sqlite3 is synchronous which also removes interleaved-await corruption within a transaction). All entry points (who-knows, fm side effect, queue) call the same `recomputeCrown()`.
3. **DB-backed job queue done right**: claim rows with an `attempts`/`status` column (process-then-delete), a **singleton** drain loop started once at boot (module-level guard; no fake-message hack, no manual `--r` duplicate-worker path), rate-limited Last.fm client shared globally.
4. **Typed schema** (Drizzle + better-sqlite3): integers as integers, booleans as booleans, real timestamps; explicit event payloads (crown type carried in the event, not inferred from API exceptions).
5. **Config over hardcoding**: prefix, owner ID, error/status channel IDs, test-guild allowlists all in config/env.

Alternatives considered: incremental refactor (rejected — duplication means every fix ×6, EOL deps force a big-bang dep jump anyway); new repo (rejected — loses history/issues continuity).

## Steps

Ordering note: steps 1–2 are the foundation; 3–10 are roughly dependency-ordered but 5–9 can partially interleave. TDD throughout: fixture-driven tests per module as it's built, not a test phase at the end.

1. **Scaffold** — branch `matt/feed1-rewrite`; remove old tree from working copy (git history keeps it; also keep a `legacy` git tag for easy reference); init TS project: `tsconfig` (strict), eslint+prettier, vitest, `src/` layout (`core/ lastfm/ db/ render/ commands/ jobs/`), `package.json` scripts (`dev`, `build`, `test`, `lint`, `typecheck`, `migrate`), `.env.example` (DISCORD_TOKEN, LASTFM_API_KEY, PREFIX, OWNER_ID, ERROR_CHANNEL_ID, STATUS_CHANNEL_ID, DB_PATH), config loader with zod validation. Keep `images/no_album.png`, fonts, `avatar.png`.
2. **DB schema (Drizzle)** — tables: `users` (discordUserId unique, lastfmUsername, rym prefs columns), `crowns`, `album_crowns` (typed integer counts, unique indexes as before), `disables`, `notif_prefs` (merge notifs/wnotifs into one row with `onWin`/`onLoss` booleans), `artist_cache`/`album_cache`, `crown_jobs` (unified artist+album queue with kind, status, attempts, snapshot fields), `crown_audit` (unified records), `scan_timings` (replaces times/totalsAndAvgs). Migrations via drizzle-kit. Drop: ryms, guesses, RYMmaxplus.
3. **Last.fm client** — typed wrappers for the 7 endpoints used (`user.getinfo/getrecenttracks/gettopalbums/gettoptracks/gettopartists`, `artist.getinfo`, `album.getinfo`); global token-bucket rate limiter (~4 req/s), retry/backoff on codes 8/16/29, typed `LastfmError`; response types match only the fields actually consumed. Vitest fixtures recorded from real responses.
4. **Core runtime** — client bootstrap (intents: Guilds, GuildMessages, MessageContent, GuildMembers) with a **startup preflight** that fetches members of one guild and fails loudly if the GuildMembers/MessageContent portal flags are missing; message router (prefix, alias-aware registry, disable checks, DM handling per old semantics), user resolution helper (author/mention, `noLogin` snippet), error reporting service (posts to error channel, chunked; global handlers; NO stderr monkey-patching — a proper logger with a Discord transport), status reporting, graceful shutdown. Disable semantics: disables are stored and checked by **canonical command name**; the router resolves any alias to its canonical name before the disable check, and `&disable`/`&enable` canonicalize their argument (so disabling `f` disables `fm` and vice versa) — router tests cover `fm/f`, `plays/p`, and generated period aliases. Per-user command cooldown (2s) as a UX guard against accidental double-fires; actual API protection comes from the global Last.fm token bucket (step 3) plus a per-guild concurrency cap of 1 on member-fan-out operations (who-knows, crown recompute).
5. **Crown service + jobs** — `recomputeCrown(guild, artist[, album])` implementing the old rules with two **explicit, intentional behavior changes**: (a) ties keep the incumbent (replacing alphabetical-flip nondeterminism), (b) the album min-plays>0 creation rule is applied to artist crowns too (old code creates artist crowns at 0 plays, `wk.js:265`) — both covered by dedicated tests (zero-listener artist, zero-listener album, exact-tie takeover) and listed in the PR description for veto. Owner-left reassign preserved; explicit event payloads carry crown kind (no inference-by-exception). Per-key mutex; writes audit + timing rows; emits win/loss DM notifications per `notif_prefs`. Job worker: singleton drain loop over `crown_jobs` started once at boot (claim → process → delete, attempts capped at 3, backoff on retryable codes, 10s spacing; test covers double-start being a no-op and crash-recovery of claimed-but-unfinished jobs). Commands: `&c`/`&ac` (crown lists, sort flags, pagination — no URL-shortener writes), `&cb`/`&acb` (leaderboards), `&notifywin`/`&notifyloss` (toggle), `&artq`/`&albq` (queue status embed with simplified ETA from `scan_timings`).
6. **fm + profile commands** — `&fm`/`&f` faithful port: two-phase loading render, exact embed/footer formats incl. the three crown gifs, `&ast` escaping, `[no album]`, album-rank scans (single sane page-depth policy), not-playing fallbacks with exact strings; crown side effect becomes **enqueue** of album+artist crown jobs (same eventual behavior, no longer blocks the command or hammers the API inline). `&login` (` | ` split, getInfo validation), `&logout`, `&mylogin`, `&lfm`, `&plays`/`&p` (plain text, exact format), `&list`.
7. **Tops / who-knows / charts** — who-knows: `&wk <artist>` (artist) and `&a <album>` (album) — `&w` stays the weekly chart, matching the old command map: sequential member fan-out through the rate-limited client, exact embed format, pagination; calls crown service at the end. Chart commands `w/m/3m/6m/y/o` + `&chart` args form: canvas grid renderer preserving tile size, overlay color coding, stats footer, progress reactions; `&nt` no-titles variant; chart runs enqueue crown jobs with a config-driven page cap (default 5, per-guild override in config replacing the hardcoded `Infinity` guilds — Matt's guilds get the old unlimited depth via config, not code). "My #N ranked" family as one definition × (media type, period) table — fixing the a6m/ao period bugs. `&chset`/`&ch`.
8. **RYM commands** — all URL builders (`rym/rstat/rstats/rcomp/rr/ry/rg/rart/rw/wg/rn`), prefs (`rpp/max/wmax/tset/tmax`), randomizers (`rand/wrand/trand/srand`) with button-based pagination (discord.js v14 buttons replace reaction paging everywhere — reactions are laggy and permission-fragile).
9. **Admin & ops commands** — `&disable`/`&enable` (revived from retired, MANAGE_GUILD, canonical-name semantics per step 4), `&help` (generated from registry — every command definition carries `name`, `aliases`, `usage`, `description` as required fields of the registry type, so the compiler enforces the metadata audit the old code lacked; help output tested for aliases and generated families), `&ping`, `&botinfo`, owner-only `&r` (graceful restart via systemd). **No eval.** Backup job: 12-hourly SQLite `VACUUM INTO` snapshot + users CSV, keep 20, report to status channel, plus off-box push (scp/rclone target configurable; default: GitHub private repo via deploy key).
10. **Test harness & live smoke** — fake-Discord layer (in-memory Message/Channel/Guild/Member stubs) driving the real router; fixture-backed Last.fm mock (nock); crown-service property tests (race: two concurrent recomputes converge; queue crash-recovery: unprocessed job survives restart). Live smoke script (env-gated): DEV token in guild 671074176622264320, tester bot sends `&ping`, `&fm`, `&login`... asserts replies (requires the third bot app — deferred until Matt creates it; script ships regardless).
11. **CI/CD** — GitHub Actions: `ci.yml` (push/PR: install, lint, typecheck, vitest); `deploy.yml` (master: build, rsync over SSH to Oracle VM, then **stop service → backup DB → `drizzle-kit migrate` → start service** so migrations never race a writing process). feed1 uses its own `DB_PATH` (`.data/feed1.sqlite`), fully separate from the legacy `.data/database.sqlite`, so the old bot can run in parallel during cutover and rollback = restart the old service. `deploy/` dir: provisioning script (node via fnm, canvas native deps incl. pango/cairo, fonts, systemd unit, logrotate), `feed1.service`, README with Oracle setup steps for Matt. Secrets via `gh secret set` (repo is personal → `mxttbennett` account).
12. **PR** — conventional title `feat(rewrite): rewrite as feed1 — typescript, discord.js v14, drizzle`, `## What & why` body, self-assigned to `mxttbennett`.

## Risks & open questions

- **Rate limits with job queue always-on**: old system relied on the queue being manually gated. Mitigation: global limiter + 10s job spacing preserves effective old cadence.
- **Canvas on ARM/Oracle**: node-canvas prebuilds exist for linux-arm64; provisioning script installs build deps as fallback. Verify early in step 11.
- **discord.js v14 GuildMembers privileged intent** must be enabled in the dev portal for both bots (needed for who-knows member fan-out) — Matt action; mitigated by the startup preflight (step 4) and a live-smoke assertion that member fetch works, so a missing flag fails at boot, not mid-command.
- **Prefix confirmation**: config-driven; README says `&`; confirm with Matt what prod uses before cutover (cosmetic — env var).
- **Behavior fidelity vs fix tension**: deliberate changes (ties keep incumbent, min-plays on artist crowns, buttons over reactions, &fm side effect async) are improvements but visible; called out in PR description for Matt to veto.
- Old `.data/database.sqlite` migration is explicitly deferred (fresh start) — `restore_users.js` CSV format documented in findings for the later migration script.
